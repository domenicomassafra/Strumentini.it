## 4. Deliberately NOT implemented

There is no email provider configured anywhere (there is no mail binding, no API token, no queue), so the account API is deliberately smaller than a typical one. All of this is intended, not pending:

- **No provider-access OAuth** — Google sign-in exists for authentication only (nonce + ID-token verification). The app stores no Google access/refresh token and has no generic provider-data OAuth flow.
- **No magic link** — sign-in is email plus password only.
- **No second factor / 2FA / TOTP** — no secret storage, no enrolment route.
- **No email delivery** — the worker never sends mail; `wrangler.jsonc` declares exactly two bindings (`ASSETS`, `AUTH_DB`).
- **No forgotten-password reset** — impossible without email. Changing a password while signed in does exist (`POST /api/auth/password`); getting back in after losing it does not, and is not described as if it did.
- **No "remember me"** — `worker/auth.ts` always issues one 30-day `HttpOnly; Secure; SameSite=Lax` cookie, so no control pretends otherwise.
- **No server-side storage of anything a tool produces** — D1 holds the account record (email, name, PBKDF2 hash, sessions) and the kept tool ids only.

The account API is **optional at deploy time**: publish the static `dist/` alone and every tool, preference and workspace feature still works; the account components detect the unreachable API and report the account as unavailable instead of faking a session. Never render a control the running deployment cannot honour.

Also out of scope, permanently: ads, generic AI features, runtime plugins, offline/PWA marketing claims, popularity claims (there is no usage data to rank by), and the retired ledger-era shell.

### Public account API state

The account API is exposed under the production custom domain `https://strumentini.it/api/auth/*`; the current Wrangler Worker target is `strumentini`, while D1 database `strumentiutili-auth` remains the intentional legacy data identifier. Checked `workers.dev` hostnames currently return 404 and are not release authority. On 2026-10-07 clean revision `eb1ccfb` / source `61b7fc66…` was deployed to the custom domain as version `a38c668c…`, passed Chromium/Firefox/WebKit plus metadata/auth smoke and representative byte-identity checks, was rolled back for real to previous known-good version `e0acf436…` with the new password-strength sentinels disappearing, and was restored successfully to `a38c668c…`; the sentinels and byte identity returned after restore. Ticket 283 now remains open only because legacy `https://strumentiutili.it/` still serves the older Vercel site instead of redirecting to Strumentini.it. The real D1 database has both migrations, server-side Turnstile remains active for password login/registration, and `npm run acceptance:auth` passes 130/130. Google Identity Services is implemented auth-only: nonce cookie + ID-token verification against Google JWKs, no Google access/refresh token storage. Production intentionally returns 503 from `/api/auth/google/config` until the owner creates a Google Web OAuth client and supplies `GOOGLE_CLIENT_ID`; the UI hides Google while that configuration is absent.

Three deployment-owner checks remain outside the repo:

1. **Outer rate limiting.** The Worker has its own sliding window (10 failed attempts per IP per 15 minutes). The required user-controlled Cloudflare zone is now active for `Strumentini.it`; this repository still has no receipt proving an outer WAF rate-limit rule in front of `/api/auth/*` is configured and effective.
2. **Billing plan.** PBKDF2-HMAC-SHA256 at 600,000 iterations measured ~81 ms per hash on the owner's machine. The repo cannot attest the Cloudflare account's billing plan; confirm Workers Paid before treating password flows as production capacity.
3. **Google client ID.** In Google Auth Platform create a **Web application** OAuth client, authorize the actual production origin `https://strumentini.it` (plus any separate preview origin only if it is deliberately enabled), then configure that client ID on the Worker as `GOOGLE_CLIENT_ID`. The implementation does not require a client secret.

## Thesis

Build a personal utility workspace for knowledge work, not another generic directory of online tools.

Current target wedge:
- freelancers;
- consultants;
- solopreneurs;
- professional creators;
- small-agency operators.

A short role-aware onboarding generates a small starter toolbox. Users can then add/remove individual tools and professional packs. This is no longer only a plan: `/onboarding/` writes the starter set, `/preferiti/` and `/impostazioni/` read and edit the same local state, and the tool cards and header chip reflect it.

## Candidate differentiators

Now shipped, not hypothesised:

- onboarding selects the first toolset automatically;
- reusable profile defaults (35 tools declare work-profile fields);
- professional packs;
- command palette / search surface (`⌘K` / `Ctrl+K`, plus `/strumenti/` and `/cerca/`);
- deterministic/local execution for every normal tool (200/200 `LOCAL`, network forbidden);
- optional sign-in, used only to carry the kept-tool list;
- portable/exportable workspace configuration.

Still unproven: whether that combination is enough to matter to anyone. It is a hypothesis, test it as one.

## Important novelty blockers

Do not claim originality from large tool count, categories, favorites, client-side privacy, all-tools-in-one-place, freelancer calculator collections or formula transparency alone.

Competitor research found partial overlaps including ToopTools, TinyWow, IT-Tools-class projects, Moderrno, freelancer toolkits and CyberChef.

Direct novelty of the current combination is NOT yet proven.

## UX

Home leads with one search field and the ten public groups, then this device's recent tools and a small editorial starter set, and closes with real numbers read from the catalog at build time. It must never open with a wall of 200 cards; the catalogue is supply infrastructure and is only allowed to feel large when someone goes looking for it (`/strumenti/`). Every count on a public surface comes from the generated catalog or quality index — never a hand-written number.

Onboarding can use profession/role, worker type, country/locale, currency, timezone, recurring tasks and common file/data formats. It produces a starter set and never blocks a first task.

## Architecture

Preferred:
- static/PWA shell;
- TypeScript;
- browser APIs;
- Web Workers;
- lazy WASM;
- local file processing;
- tiny optional sync backend;
- no remote user-file database;
- no per-use LLM requirement.

AI can be optional for onboarding suggestions or truly semantic tools. Today: none is required anywhere; the tools are deterministic.

## Brand / GTM update

Strumentini.it is the owner-selected public brand. The prior codename collision is historical and no longer defines the product identity.

Important deeper blockers:

- SolveKit already owns multi-tool workspaces and connected workflows.
- smarterfaster already uses profession-based workspace generation and professional packs.
- FreelTools already calls itself a freelancer operating system and has 242 tools.
- ToopTools already offers a personalized client-side workspace.

Current differentiation hypothesis depends on the full combination of role onboarding + shared profile + executable deterministic utilities + packs + persistent workspace + context handoff + portable config.

Read research/competitive-brand-gtm-2026-09-23.md, docs/05-brand-positioning.md and docs/06-go-to-market.md before further product work.

## Scale / free-model update

The preferred business hypothesis is deliberately compatible with being fully free, potentially open source, and useful primarily as a brand/distribution asset.

Advertising is optional and should not shape the product early. If tested later, prefer public discovery/documentation surfaces; keep the personal workspace clean and never place ads adjacent to critical tool controls.

The catalog may grow beyond hundreds of tools, but only through a Tool Factory with a single quality contract and a real implementation per tool — placeholders are prohibited. The public catalog-size claim counts every tool with a real route and implementation; certification is a separate, visible fact (`Verificato` for a Gold receipt, `In verifica` otherwise) and the two numbers are never conflated, because the site has no popularity or usage data to rank or badge by.
