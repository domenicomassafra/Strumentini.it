## 1. What this repository is now

1. An Italian-first, static Astro 7 + Preact + TypeScript site: 200 deterministic local tools, each with a real route, page, implementation and tests, generated by the in-repo Tool Factory — 168 of them certified Gold today, 32 not yet.
2. Ten public surfaces — home, `/strumenti/`, `/cerca/`, `/categorie/<slug>/`, `/tools/<slug>/`, the tool workspace, `/preferiti/`, `/impostazioni/`, `/accedi/`, `/onboarding/` — over one header and one footer, with a single visual world (one blue accent, Inter, white cards, real dark mode).
3. A local-first workspace: the installed/recent tool set, work profile and last value live in IndexedDB/`localStorage`; no file or result ever leaves the device.
4. Optional and additive on top: an account API in `worker/**` (Cloudflare Worker + D1, PBKDF2 cookie sessions) for carrying the kept-tool list across devices. With no worker deployed the whole site still works and the account surfaces say so. Current certification frontier: **168 Gold / 1 Partial (`image-resize`) / 31 unverified** of 200, from `quality/receipts/expanded-catalog-certification.json`.
5. `/library` and `/library/` are now just redirects to `/strumenti` and `/strumenti/` (`astro.config.mjs`); the old page, model and components are deleted, and nothing else in the product uses that name.

## 3. The gates and what each proves

Run from the repository root; none of them needs a secret, an account or the network.

| Command | What it proves |
|---|---|
| `npm run test` | Regenerates the catalog, verifies the certification index is current, then runs the whole Vitest suite. This is the correctness gate. |
| `npm run check` | Regenerates the catalog, verifies the certification index, then `astro check`. This is the type/template gate; 0 errors, 0 warnings and 0 hints is the expected state. |
| `npm run build` | The real static build plus `scripts/inspect-build.ts`. Nothing downstream is meaningful if this fails. |
| `npm run acceptance:discovery` | A real browser against the built site: `/strumenti/` query/paging/group views, `/cerca/` results and honest zero-result continuation, the command palette, focus restoration, URL/reload/back preservation, and no eager tool chunk. Writes `quality/receipts/discovery/acceptance.json`. |
| `npm run deploy:check:portable` | `dist/` is genuinely portable: required pages present, no server-runtime artifacts (`_worker.js`, `functions/`), no provider-only origin, no absolute developer paths, canonical origin present. |
| `npm run acceptance:auth` | The account API end to end against `wrangler dev` and a throwaway local D1: register, login, session, profile, password change, session list/delete, account delete and favourites, plus the cookie attributes, generic login message and login throttling. |
| `npm run acceptance:expanded-local` | The 49-tool expanded-local batch driven through the built static site. |

Heavier, receipt-producing variants: `npm run acceptance:family-matrix` and `npm run acceptance:browser-performance` regenerate the browser matrices; `npm run release:validate` chains catalog + build + `scripts/validate-release.ts`. Treat all three as evidence generators, never as a substitute for the gates above.

Before committing anything: `npm run test`, `npm run check`, `npm run build`, then the three acceptance gates, **and** re-generate the receipts the change invalidates (see §5). The evidence fingerprint covers `src/`, `scripts/`, `tests/`, `public/`, `quality/{fixtures,oracles}/` and the root config files — any source edit invalidates every receipt again.

## 4. Deliberately NOT implemented

There is no email provider configured anywhere (there is no mail binding, no API token, no queue), so the account API is deliberately smaller than a typical one. All of this is intended, not pending:

- **No OAuth / social login** — there is no `/api/auth/oauth*` route and no provider client id anywhere; `/accedi/` renders no social buttons.
- **No magic link** — sign-in is email plus password only.
- **No second factor / 2FA / TOTP** — no secret storage, no enrolment route.
- **No email delivery** — the worker never sends mail; `wrangler.jsonc` declares exactly two bindings (`ASSETS`, `AUTH_DB`).
- **No forgotten-password reset** — impossible without email. Changing a password while signed in does exist (`POST /api/auth/password`); getting back in after losing it does not, and is not described as if it did.
- **No "remember me"** — `worker/auth.ts` always issues one 30-day `HttpOnly; Secure; SameSite=Lax` cookie, so no control pretends otherwise.
- **No server-side storage of anything a tool produces** — D1 holds the account record (email, name, PBKDF2 hash, sessions) and the kept tool ids only.

The account API is **optional at deploy time**: publish the static `dist/` alone and every tool, preference and workspace feature still works; the account components detect the unreachable API and report the account as unavailable instead of faking a session. Never render a control the running deployment cannot honour.

Also out of scope, permanently: ads, generic AI features, runtime plugins, offline/PWA marketing claims, popularity claims (there is no usage data to rank by), and the retired ledger-era shell.

### Before the account API is exposed publicly

The API is implemented and its acceptance suite passes (`npm run acceptance:auth`, 121 checks against a real local Worker + D1). Four things are deliberately left to the owner, because each one needs a credential or a dashboard action that code cannot supply:

1. **A real D1 `database_id`.** `wrangler.jsonc` declares the binding and the migrations directory but no `database_id`; create the database (`npx wrangler d1 create strumentiutili-auth`), paste the id into the binding, then `npx wrangler d1 migrations apply AUTH_DB --remote`.
2. **Bot protection server-side.** Registration and sign-in currently accept any well-formed request from any client. Add a challenge (Cloudflare Turnstile) verified **inside the Worker** — a browser-only check protects nothing — or accept the risk knowingly.
3. **Rate limiting in front of `/api/auth/*`.** The Worker has its own sliding window (10 failed attempts per IP per 15 minutes), but it runs *after* the request has already cost a Worker invocation. Add a Cloudflare rate-limiting rule on that path as the outer layer.
4. **The plan that matches the hashing cost.** PBKDF2-HMAC-SHA256 at 600,000 iterations measured **~81 ms** per hash here. The Free plan's per-request CPU budget is 10 ms, so the account API needs Workers **Paid**. The static site does not: it can be served on any plan, or on any host.

Deploying the static site and the API are separable. `dist/` alone is a complete product.

## 5. Known gaps

1. **Two orphaned page wrappers.** `src/components/tools/file-privacy/FilePrivacyPage.astro` and `src/components/tools/research-knowledge/ResearchKnowledgePage.astro` are imported by nothing — all 200 pages render through `src/components/tools/shared/ItalianToolPage.astro`. Their sibling *tool* components and the `research-knowledge/index.tsx` barrel are real and in use; only these two page shells are dead. Delete them, or move them onto the shared contract deliberately.
2. **Receipts: which are fresh and which are not.** The per-tool certification receipts bind to a source fingerprint, so any edit — including this redesign — invalidates them by construction. Recompute the working-tree fingerprint with `currentEvidenceSourceFingerprint()` from `scripts/lib/current-revision.ts` and it matches none of the fingerprints recorded under `quality/receipts/`. Concretely:
   - `quality/receipts/discovery/acceptance.json` — **regenerated** (`npm run acceptance:discovery`); current.
   - `quality/receipts/browser-performance/fresh-browser-matrix.json` — **regenerated** (`npm run acceptance:browser-performance`); five engines PASS. Its `freshAcceptance` sibling entries are only as good as the scripts they run.
   - `quality/receipts/cross-family/browser-acceptance.json` and `quality/receipts/onboarding/browser-acceptance.json` — **regenerated**; both PASS.
   - every per-tool Gold receipt — **stale**: they target pre-redesign source content. Regenerate family by family with the `gold:*` scripts after committing. This is the single largest reason `npx tsx scripts/validate-release.ts` still reports blockers, and it must not be worked around by loosening the validator.
   - `quality/receipts/release/validation.json` and `quality/receipts/release/rollback.json` — still the `cd3b2f2` generation. Rollback stays `UNPROVEN` until a real Cloudflare deploy + rollback is exercised; do not invent it. `WORKTREE_DIRTY` is expected while the redesign is uncommitted.
3. **Uncommitted tranche hygiene.** The redesign is one dirty tree: staged deletions, untracked new paths and unstaged modifications. The throwaway working aids (`scripts/_dbg{,2,3,4}.mjs`, `scripts/account-pages-check.mjs`, `.screenshots/`) have been removed. `design/references/redesign-20261003/` **stays**: it is the ten reference screens this design was built from, and the authority for the next fidelity pass.
4. **`ROADMAP.md` is stale**: it still quotes the pre-redesign 119/1/80 frontier and a retired UI tranche. `PROJECT-STATUS.md` and `HANDOFF.md` are current.
5. **Two certification-sensitive leftovers in the generated catalog path**: `toLegacyCatalogSummary` / `renderLegacyCatalogSource` keep a second, lossier summary schema alive. Consolidate before adding any non-local runtime variant.

## Thesis

Build a personal utility workspace for knowledge work, not another generic directory of online tools.

Current target wedge:
- freelancers;
- consultants;
- solopreneurs;
- professional creators;
- small-agency operators.

A short role-aware onboarding generates a small starter toolbox. Users can then add/remove individual tools and professional packs. This is no longer only a plan: `/onboarding/` writes the starter set, `/preferiti/` and `/impostazioni/` read and edit the same local state, and the tool cards and header chip reflect it.

## Candidate differentiators

Now shipped, not hypothesised:

- onboarding selects the first toolset automatically;
- reusable profile defaults (35 tools declare work-profile fields);
- professional packs;
- command palette / search surface (`⌘K` / `Ctrl+K`, plus `/strumenti/` and `/cerca/`);
- deterministic/local execution for every normal tool (200/200 `LOCAL`, network forbidden);
- optional sign-in, used only to carry the kept-tool list;
- portable/exportable workspace configuration.

Still unproven: whether that combination is enough to matter to anyone. It is a hypothesis, test it as one.

## Important novelty blockers

Do not claim originality from large tool count, categories, favorites, client-side privacy, all-tools-in-one-place, freelancer calculator collections or formula transparency alone.

Competitor research found partial overlaps including ToopTools, TinyWow, IT-Tools-class projects, Moderrno, freelancer toolkits and CyberChef.

Direct novelty of the current combination is NOT yet proven.

## UX

Home leads with one search field and the ten public groups, then this device's recent tools and a small editorial starter set, and closes with real numbers read from the catalog at build time. It must never open with a wall of 200 cards; the catalogue is supply infrastructure and is only allowed to feel large when someone goes looking for it (`/strumenti/`). Every count on a public surface comes from the generated catalog or quality index — never a hand-written number.

Onboarding can use profession/role, worker type, country/locale, currency, timezone, recurring tasks and common file/data formats. It produces a starter set and never blocks a first task.

## Architecture

Preferred:
- static/PWA shell;
- TypeScript;
- browser APIs;
- Web Workers;
- lazy WASM;
- local file processing;
- tiny optional sync backend;
- no remote user-file database;
- no per-use LLM requirement.

AI can be optional for onboarding suggestions or truly semantic tools. Today: none is required anywhere; the tools are deterministic.

## Brand / GTM update

StrumentiUtili.it is the owner-selected public brand. The prior codename collision is historical and no longer defines the product identity.

Important deeper blockers:

- SolveKit already owns multi-tool workspaces and connected workflows.
- smarterfaster already uses profession-based workspace generation and professional packs.
- FreelTools already calls itself a freelancer operating system and has 242 tools.
- ToopTools already offers a personalized client-side workspace.

Current differentiation hypothesis depends on the full combination of role onboarding + shared profile + executable deterministic utilities + packs + persistent workspace + context handoff + portable config.

Read research/competitive-brand-gtm-2026-09-23.md, docs/05-brand-positioning.md and docs/06-go-to-market.md before further product work.

## Scale / free-model update

The preferred business hypothesis is deliberately compatible with being fully free, potentially open source, and useful primarily as a brand/distribution asset.

Advertising is optional and should not shape the product early. If tested later, prefer public discovery/documentation surfaces; keep the personal workspace clean and never place ads adjacent to critical tool controls.

The catalog may grow beyond hundreds of tools, but only through a Tool Factory with a single quality contract and a real implementation per tool — placeholders are prohibited. The public catalog-size claim counts every tool with a real route and implementation; certification is a separate, visible fact (`Verificato` for a Gold receipt, `In verifica` otherwise) and the two numbers are never conflated, because the site has no popularity or usage data to rank or badge by.
