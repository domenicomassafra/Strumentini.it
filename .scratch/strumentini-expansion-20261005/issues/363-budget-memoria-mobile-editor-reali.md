## 2026-10-14 worker-2 — unsupported Worker resource action falsely releases live memory (RED → GREEN; OPEN)

**Reproducible P1 fail-open in actual utility/runtime consumer:** `src/runtime/heavy-local-job.ts` handled a worker packet `type:"resource"` using `action === "reserve" ? reserve() : release()`; every unrecognized action was therefore interpreted as a valid release of the named reservation. A real `node:worker_threads` Worker can send arbitrary structured-clone values, irrespective of TypeScript's declared union. In newly added `tests/heavy-local-memory-363-20261014-resource-action.test.ts`, the actual Worker allocates and retains a 384-byte `Uint8Array` frame, sends a proper `reserve`, then posts `action:"discard-without-freeing"` without freeing its array. The old main thread *silently releases the accounted 384 bytes*, lets the same live Worker allocate/reserve another 384-byte frame, and accepts a `success` containing `liveFrameBytes:768` under a configured **700-byte hard working-set limit**, falsely reporting peak accounted working set **480 bytes** (64 input + 32 caller-owned preview + 384 claimed live frame). RED Vitest exit 1: **promise resolved** with the invalid 768-byte result rather than the expected `PROTOCOL_ERROR`. Added real `worker_threads` forged-packet tests for both aliases, each holding the original 384-byte binary frame while attempting to hide it from the resource accountant. The failure path terminates the Worker, releases the owned preview exactly once and resets resource accounting, without publishing the false-success result or destroying a previously verified output. The tests use genuine worker threads and real binary frame allocations, an external cleared RED-only watchdog, await all actual `exit` events, prove previous valid output persists, and verify a later valid `release` and retry still succeed with a zero final accounted working set.
